Data node

A node can also display a grid of typed numeric values instead of a plain text label — see DataNodeContent. Each value's bytes are shown in big-endian format (most-significant-byte first), space-separated, with no 0x prefix.

Without additional formatting, a string consisting of multiple bit values cannot indicate where one value ends and the next begins; consequently, each value is displayed its own small box, coloured according to its type — a pastel shade per u8, u16, u32, u64. The signed equivalents (i8, i16, i32, i64) are given a deeper shade of the same colour.

With a single value, the type-specific background colour is applied directly to the node's own box, since there are no sibling values from which it needs to be distinguished.

Each of the first four rows below shows one integer width as both a single value (left) and several values (right).

The multi-value counts are deliberately varied to cover every shape the grid layout rule can produce: u8 uses 8 values, which divides evenly by a power of two (2 rows of 4); u16 uses 5, which has no power-of-two divisor at all, so it falls back to the closest-to-square shape (3 rows of 2, one slot left blank); u32 uses 9, a perfect square with no power-of-two divisor either, which that same fallback happens to fit exactly (3 rows of 3); and u64 uses 4, both a perfect square and evenly divisible by a power of two, where the two rules agree on the same 2×2 shape. Every box is sized to fit its own content automatically, and every box is draggable, exactly like any other node.

The fifth row is a single u64 value under binary formatting: 64 digits, nybble-grouped and byte-separated. The grid layout rule sizes a row by cell count, not physical width, so a single very long value like this one renders far wider than it is tall. This is the extreme case GridLayout::MaxColumns exists to let a caller cap.

The sixth row shows the signed widths. A sign is shown only when a value is negative, so -5 has one and 42 has none. Hexadecimal and binary show the value's two's-complement representation, so -2 as an i16 reads FF FE, in the default big-endian byte order.

The last two rows show the same u8 bytes as a hex dump, in the format of hexdump -C: the bytes in hexadecimal, eight to a group, and then as characters, with anything that is not printable shown as .. Each line holds sixteen bytes and is a cell of its own. The first row hides each line's offset, which is the default. The second shows it, together with the line that ends the dump with its total length, and has a label, so that it sits in a labelled box.
