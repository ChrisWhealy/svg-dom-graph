128-bit values and UUIDs

A data node can hold both signed (i128) and unsigned (u128) 128-bit values. It can also hold Uuid identifiers, which are also 128 bits wide, but are never treated as numbers. Each is a type of its own, having its own colour and name for assistive technology.

Integers

A u128 runs to 39 decimal digits, so the largest value it can hold is far wider than anything a u64 can hold. An i128 shows a sign only when it is negative. When displayed in hexadecimal, it is shown in two's complement format: -1 is sixteen bytes of FF.

In terms of rendering width, this is the widest value a i128 data node can hold, since the minus sign makes it one character longer than the largest positive value.

UUIDs

A Uuid is written by DataFormat::Uuid, as grouped hexadecimal digits. Its version is the first digit of its third group, so v4 shows a 4 there. The nil and max UUIDs have no version. Under DataFormat::Decimal the same value would be rendered as a number.

IMPORTANT: Nothing checks that the bits being displayed represent a valid UUID. Any 128-bit value can be shown as if it were a UUID.

Formats

A UuidFormat controls the formatting. This controls both the case of the hexadecimal digits, and whether the UUID grouped values are hyphenated, unhyphenated (simple), braced or shown as a URN.

A UUID cannot be supplied as the operand of any operator, since this value always function as as an identifier, and not a number. If you need a number, use either a u128 or a i128.

Byte layouts

A UUID of RFC 9562 is stored in big-endian format (most significant byte first), so its bytes layout in memory is the same as the printed order of its digits.

However, when held in memory, a Microsoft GUID stores the first three UUID fields the other way round (little endian format), so the same UUID has different in-memory byte order.

If you are not aware of this detail and the UUID is displayed using the wrong layout, then the byte order of the UUID's first three fields will be reversed, as the last line shows.
