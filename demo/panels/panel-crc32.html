CRC-32

A cyclic redundancy check detects accidental changes to data. The sender calculates a short number from the data it is sending, then sends this number along with the data.

The receiver calculates the same number from the data it received. If the two check numbers differ, then it is known that the data changed during transmission.

CRC-32 is used by Ethernet, zip, zip and PNG to protect against data corruption during transmission. It finds every change of a burst of up to 32 bits, and all but one in four billion of the others. It does not defend against a person changing the data on purpose, since anyone can calculate a new check number after they have tampered with the data.

CRC-32 treats the data as one very long binary number and takes the remainder when it is divided by a fixed polynomial. It uses calculations that do not result in arithmetic carries, so that adding becomes the same as XOR.

The version demonstrated here is the one every common tool uses. The polynomial is 0xEDB88320, which is the usual 0x04C11DB7 with its bits in reverse order, since the register is shifted to the right.

  1. The 32-bit register starts as all ones: 0xFFFFFFFF.
  2. For each input byte, XOR the byte with the lowest byte of the register. The result is an index from 0 to 255 into a table.
  3. The table's entry for that index is what shifting a byte through the register one bit at a time would have done: shift right by one, and if the bit that fell out was a one, XOR in the polynomial. Doing that eight times for every possible byte makes the 256 entries, so the demo takes each byte in one step.
  4. The new register is the old register shifted right by a byte, XORed with the table's entry.
  5. After the last byte, XOR the register with all ones. That flips every bit, and is the CRC-32.

The standard way to check an implementation of CRC-32 is that the text 123456789 has the checksum CBF43926. Type that text to try it. The diagram opens on a longer sentence, so that there is enough to corrupt.

Correcting an error

CRC-32 is nearly always used only to detect an error, and the data is then sent again. But the check number holds enough to do more when exactly one bit has changed. The difference between the check number that was sent and the one the receiver works out is called the syndrome. It is zero if nothing changed. For a single flipped bit, it depends only on where the bit is, and not on what the data holds. This polynomial gives every bit position of data this short a different syndrome, so the receiver can work out the syndrome of each position, find the one that matches, and flip that bit back. If two bits change, no single position matches. That is detected, but it cannot be corrected.

The toolbar at the top of the diagram steps through the calculation. At the start nothing has been worked out, and every box that is still to come is drawn faint. Each step takes one more byte of the text through the register and marks it in the bytes, the table index, the table entry and the register. After the last byte come the final XOR, the arrival of the bytes at the receiver, and then each of the receiver's boxes in turn. "Next 8" moves eight steps at a time. Editing the text starts the walk again, and so does "Restart", which also removes any flipped bit.

Press "Flip a random bit" at the top of the diagram. The demo picks one bit at random, from the data or from the CRC, and flips it on the way from the sender to the receiver. If the walk has not reached the arrival of the bytes, it moves there, so that the error can be seen. Watch the receiver's column. The data flows down the sender's column, across, and then up the receiver's column. Each press picks again, and "Remove all errors" puts the bit back.

  • One bit of the data: the receiver finds which bit it is and flips it back.
  • One bit of the CRC: the data is right and the CRC is wrong. The syndrome has a single 1, which no bit of the data gives, so the receiver leaves the data alone.

Only one bit is flipped because one is all that CRC-32 can correct. When two or more bits change, the check number still shows that something is wrong, but no single position matches the syndrome, so the receiver can only ask for the data again. With several bits flipped, the syndrome can even match a single position by chance, and then the receiver would correct the wrong bit.

Type in the text input node. Each box of the diagram has a note beside it that says what it holds and how its values are worked out. The numbers in the sender's notes are the real ones for the first byte of the text, so you can follow that byte all the way through by hand. The diagram is drawn again for each change. Zoom and pan are kept. The boxes line up on one axis and cannot be dragged. Bits are counted from 0 at the least significant bit of a byte.

The checksum covers 64 bytes, so each byte can be a step in the diagram. Any text past that is not covered, the cut falls between characters, and a note to the right of the text input node says how much was left out. Every value is worked out in plain Rust. The library draws the nodes and does no checksumming.
